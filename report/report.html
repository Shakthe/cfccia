1. System Architecture Diagram

I named my system VitalWatch. The idea is simple: a patient wears a device that keeps measuring heart rate, blood pressure, oxygen level (SpO2) and body temperature. These readings go to the cloud, where my application checks them. If any reading crosses a danger limit, the system sends an alert straight back to the same wearable device, so the patient knows something is wrong right away.

I built the cloud side on Amazon Web Services (AWS). The full path of the data, from the sensors to the alert on the patient's wrist, has five layers, shown below.

Figure 1.1 — VitalWatch architecture on AWS, from wearable sensors to the alert on the patient's wearable

How the data flows through each layer

LayerWhat is thereWhat it does
1 — Edge / IoTSensors on the wearable: heart rate, blood pressure, SpO2, body temperatureKeeps measuring the patient's vital signs and sends them out
2 — AWS IngestionAWS IoT CoreEvery wearable connects here over MQTT with its own certificate. An IoT Rule picks up the readings from the topic vitalwatch/telemetry/<device_id> and passes them on
3 — Processing & AppAmazon Kinesis + Amazon EKS running my containerKinesis holds the incoming stream of readings. My Flask app (running on Kubernetes) checks each reading against the limits: heart rate above 120 or below 45 bpm, SpO2 below 90%, temperature above 38.5 °C, BP above 180/110 mmHg
4 — Alert DeliveryAWS IoT Core publish (main path) and Amazon SNS (extra path)When a limit is crossed, the app publishes the alert to that patient's own topic vitalwatch/alerts/<device_id>, which the wearable listens to. SNS can also inform doctors/family by SMS or email
5 — UsersThe patient's wearable, plus doctors and caregiversThe wearable vibrates and shows the alert to the patient. Doctors can watch everything on a live dashboard

For storage, DynamoDB would keep the patient list and old alerts, Timestream would keep the history of readings, and CloudWatch would watch the health of the system itself.

2. Creating the Docker Image

The application itself is a Python Flask service (app/app.py). Since I do not have real medical wearables, the app generates realistic readings for each registered patient (with occasional bad readings mixed in on purpose), checks every reading against the danger limits (app/alerts.py), and publishes an alert to the patient's wearable topic whenever a limit is crossed. If no real AWS IoT endpoint is given, the publish is written to the logs instead, so everything can be tested without an AWS account.

Step 1 — Write the Dockerfile

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /srv/vitalwatch

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app

RUN useradd --create-home vitalwatch
USER vitalwatch

EXPOSE 5000

HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD python -c "import urllib.request,sys; \
      sys.exit(0 if urllib.request.urlopen('http://localhost:5000/health').status==200 else 1)"

CMD ["gunicorn", "--workers", "2", "--bind", "0.0.0.0:5000", "app.app:app"]

Why I wrote it this way:

  • I picked python:3.12-slim as the base because it is a much smaller download than the full Python image. My final image came to 213 MB, so Kubernetes can pull it quickly, and a smaller image also means fewer things inside it that could have security holes.
  • The two ENV lines stop Python from writing .pyc files and make it print logs immediately, so I can see the alerts live with docker logs or kubectl logs.
  • I copy requirements.txt and install packages before copying my code. Docker caches each step, so when I only change my code, it does not reinstall all the packages again — rebuilds finish in a few seconds.
  • I made a normal user called vitalwatch and switched to it. The app never runs as root inside the container, which is safer.
  • The HEALTHCHECK keeps calling my /health endpoint. If the app stops answering, Docker and Kubernetes can see the container is unhealthy and restart it on their own.
  • I start the app with gunicorn (with 2 workers) and not with Flask's built-in server, because the built-in server is only meant for development and handles one request at a time.

Step 6 — Deploy anywhere without modification

Nothing in the image is tied to my laptop. All settings (limits, intervals, AWS endpoint) come from environment variables. So the exact image from Docker Hub runs as-is under Kubernetes — k8s/deployment.yaml simply says image: shakthe1311/vitalwatch:v1, and the CI/CD pipeline (Section 4) deploys the same image into a cluster on every push.

3. Kubernetes Deployment Architecture

All the Kubernetes files are in the k8s/ folder of the repo. They pull the same public image from Docker Hub and run it:

ResourceFileWhat it is for
Namespacenamespace.yamlPuts everything of this project in its own space called vitalwatch, away from other apps in the cluster
ConfigMapconfigmap.yamlHolds the danger limits and the monitoring interval. I can change a limit and restart the pods — no need to rebuild the image
Secretsecret.yamlHolds the AWS IoT endpoint and keys. In my demo these are empty, so the app just logs the wearable pushes instead of really sending them
Deploymentdeployment.yamlRuns 2 copies (replicas) of the container. Updates roll out one pod at a time so the service never goes fully down. Liveness and readiness probes keep hitting /health; a stuck pod gets restarted automatically
Serviceservice.yamlGives the pods one stable address. I used NodePort 30090 for my local cluster; on EKS this would just become type LoadBalancer
HPAservice.yamlAutoscaler — if average CPU goes above 70%, it grows from 2 pods up to 6, and shrinks back later

I tested all of this on a local cluster made with kind. These are the commands I ran:

kind create cluster --name vitalwatch
kind load docker-image shakthe1311/vitalwatch:v1 --name vitalwatch
kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/
kubectl rollout status deployment/vitalwatch -n vitalwatch
$ kubectl get all -n vitalwatch

4. CI/CD Pipeline Workflow

The pipeline lives in .github/workflows/ci-cd.yml. GitHub Actions runs it by itself on every push (and pull request) to main. It has three jobs, and each one only starts if the one before it passed:

JobWhat it does
Run Unit TestsInstalls the packages and runs my 8 pytest tests. If even one test fails, nothing else runs — a broken image can never get published.
Build and Push to Docker HubLogs in to Docker Hub with the repository secrets (DOCKERHUB_USERNAME, DOCKERHUB_TOKEN) and pushes the image with the tags latest, v1 and the commit id, plus labels saying which commit it was built from.
Deploy to KubernetesStarts a fresh Kubernetes cluster right inside the GitHub runner (using kind), loads the newly built image, applies all my k8s/ files, waits for the rollout to finish, and finally runs a small curl pod that calls /health through the cluster Service to prove the deployed app answers.

5. Evaluation Report with Design Justification

Why I chose each technology

ChoiceReason
AWSThe main reason is AWS IoT Core. It gives every wearable its own certificate, handles MQTT at any scale, and most importantly it can publish back down to a device. That downlink is exactly how my alert reaches the patient's wearable, which is the core requirement of this question. Kinesis absorbs the flood of readings, EKS runs my container, and SNS covers the doctors/family messages.
Python + FlaskSmall, quick to write, and easy for anyone to read. Perfect size for this kind of service.
gunicornA proper WSGI server that runs several workers, so more than one request can be served at a time. Flask's own server is only for development.
Docker (slim base)A 213 MB image that pulls fast, runs as a non-root user and checks its own health. One image, same behaviour everywhere.
KubernetesFor a patient monitor, downtime is not acceptable. Kubernetes restarts dead pods on its own, runs 2+ copies, updates them one by one with zero downtime, and keeps settings and secrets outside the image.
GitHub ActionsIt is already part of GitHub, free for public repos, and the whole pipeline sits in one YAML file in the repo where anyone (including the evaluator) can read it.

Design decisions

  • The alert goes to the patient's own wearable. Each device listens on its own topic vitalwatch/alerts/<device_id>, and the app publishes the alert exactly there. This is the requirement of Question 2, and it is the main path of the design, not an afterthought.
  • The checking code does not care where readings come from. alerts.evaluate() just takes a reading and returns alerts. Today the readings come from my simulator; tomorrow they can come from real IoT Core telemetry, and the alert code does not change at all.
  • All settings are environment variables. Limits, the monitor interval and the AWS endpoint come from the ConfigMap and Secret. The same image goes from my laptop to a real cluster without being rebuilt. A hospital could even set stricter limits for a cardiac ward just by changing the ConfigMap.
  • The demo never breaks. If the AWS endpoint is empty, the app logs the wearable push instead of crashing. Put a real endpoint in the Secret and the real MQTT publish happens — no code change.
  • 2 replicas + autoscaler. Two pods mean one can die and patients are still being monitored. The HPA adds pods when load grows, for example when many more patients are added.
  • The limits are medically sensible. Heart rate above 120 (tachycardia) or below 45 (bradycardia), SpO2 below 90% (low oxygen), temperature above 38.5 °C (fever) and BP above 180/110 (hypertensive crisis) are standard warning levels, so the alerts mean something and do not spam the patient.

Limitations

  • Patients and alert history live in the app's memory, so they are lost when a pod restarts. A real deployment would keep them in DynamoDB and the readings in Timestream.
  • The wearable push is simulated (logged) in my demo instead of a real AWS IoT Core publish.
  • The vital signs come from a simulator, not from real sensors.
  • Everything runs in one region; there is no failover to a second region yet.

6. Conclusion and Future Enhancements

Conclusion

VitalWatch covers the complete journey asked for in Question 2. Vital signs (heart rate, blood pressure, SpO2, body temperature) are collected non-stop for every registered patient, each reading is checked against clear medical limits, and the moment something is wrong the alert is pushed to that patient's own wearable device, with doctors and family covered through SNS as a second channel. The app is packed into a Docker image that anyone can pull from Docker Hub (shakthe1311/vitalwatch:v1), it runs on Kubernetes with health probes, two replicas, autoscaling and zero-downtime updates, and every push to GitHub is tested, built, published and deployed automatically by the Actions pipeline. Since the design sits on managed AWS services (IoT Core, Kinesis, EKS, SNS, DynamoDB), the same architecture would carry over to a real hospital deployment.

Future enhancements

  • Real wearables — connect actual BLE devices through a small gateway to AWS IoT Core instead of the simulator.
  • Proper storage — DynamoDB for patients and alert history, Timestream for the reading history and trends.
  • Smarter alerts — use anomaly detection on the trend of a patient's vitals to warn before a hard limit is crossed, and tune limits per patient.
  • Fog layer at home — run the limit checks on a small box in the patient's house (AWS IoT Greengrass) so alerts still work even when the internet is down.
  • Escalation — if the patient does not acknowledge the alert on the wearable, automatically inform the doctor or emergency services; connect to hospital record systems (FHIR).
  • Security and privacy — encryption end to end, audit logs, and handling patient data as per healthcare rules like HIPAA.
  • Monitoring the monitor — Prometheus and Grafana dashboards plus CloudWatch alarms on the system itself.
  • Two regions — run the cluster in a second region with automatic failover so even a region outage does not stop patient monitoring.
