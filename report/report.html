1. System Architecture Diagram

VitalWatch is designed as a five-layer, cloud-native pipeline on Amazon Web Services (AWS) that takes raw vital-sign telemetry from a patient's wearable device all the way through to an alert delivered back to that same wearable, so the patient is warned the moment any vital sign becomes dangerous.

Figure 1.1 — VitalWatch five-layer cloud architecture on AWS

Layer-by-layer flow

LayerComponentRole
1 — Edge / IoTWearable sensors: heart rate (PPG), blood-pressure cuff, SpO2 pulse oximeter, body-temperature sensorGenerates continuous vital-sign telemetry for each registered patient
2 — AWS IngestionAWS IoT CoreDevice registry, X.509 certificate authentication, and MQTT telemetry ingestion at scale; an IoT Rule routes vitalwatch/telemetry/<device_id> into the stream
3 — Stream Processing & AppAmazon Kinesis Data Streams + Amazon EKS (Flask app, ConfigMap/Secrets, HPA)Evaluates every reading against clinical thresholds (HR >120 or <45 bpm, SpO2 <90%, temperature >38.5 °C, BP >180/110 mmHg) and runs the containerized application
4 — Alert DeliveryAWS IoT Core downlink publish (primary) + Amazon SNS (secondary)Pushes the alert to the patient's wearable over MQTT topic vitalwatch/alerts/<device_id>; SNS notifies the care team by SMS/email
5 — UsersPatient wearable + clinicians/caregiversThe wearable vibrates and displays the alert to the patient; clinicians follow the live dashboard

Supporting services: Amazon DynamoDB (patient registry and alert history), Amazon Timestream (vitals time-series for trend analysis) and CloudWatch (observability).

2. Creating the Docker Image

The application is a Python Flask service (app/app.py) that simulates the four wearable vital-sign streams (heart rate, blood pressure, SpO2, body temperature) for every registered patient, evaluates each reading against clinical thresholds (app/alerts.py) and pushes alerts to the patient's wearable device over MQTT (simulated when no AWS IoT endpoint is configured, real IoT Core publish when one is).

Step 1 — Write the Dockerfile

The Dockerfile defines how the application is packaged:

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /srv/vitalwatch

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app

RUN useradd --create-home vitalwatch
USER vitalwatch

EXPOSE 5000

HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD python -c "import urllib.request,sys; \
      sys.exit(0 if urllib.request.urlopen('http://localhost:5000/health').status==200 else 1)"

CMD ["gunicorn", "--workers", "2", "--bind", "0.0.0.0:5000", "app.app:app"]
  • Base image: official lightweight Python 3.12 runtime. The slim variant keeps the final image small (213 MB vs ~1 GB for the full image), which speeds up pulls in Kubernetes and reduces attack surface.
  • Environment settings: disables .pyc files and forces real-time log output so docker logs / kubectl logs show wearable alert pushes immediately.
  • Security best practice: the container runs as a non-root user (vitalwatch), limiting damage in case of compromise.
  • Layer caching optimization: dependencies are copied and installed before the source code, so editing code never re-downloads packages — rebuilds take seconds.
  • Port + self-healing: documents port 5000 and lets Docker/Kubernetes detect an unhealthy container automatically via the /health endpoint.
  • Production server: gunicorn (WSGI) instead of Flask's dev server — 2 worker processes handle concurrent requests.

4. CI/CD Pipeline Workflow

The pipeline is defined in .github/workflows/ci-cd.yml and runs automatically on every push (and pull request) to main:

JobWhat it does
Run Unit TestsInstalls dependencies and runs the 8-test pytest suite; a failure blocks everything downstream.
Build and Push to Docker HubLogs into Docker Hub using repository secrets (DOCKERHUB_USERNAME, DOCKERHUB_TOKEN) and pushes tagged images (latest, v1 + commit-SHA tag) with OCI labels (title, source, revision) only after tests pass.
Deploy to KubernetesCreates a Kubernetes cluster in the runner (kind), loads the freshly built image, applies the k8s/ manifests, waits for rollout status, and runs a smoke test that curls /health through the cluster Service.

Secrets are configured under Repo → Settings → Secrets and variables → Actions. 5. Evaluation Report with Design Justification

Technology stack

ChoiceJustification
AWSAWS IoT Core is a managed, scalable MQTT gateway with per-device X.509 authentication — essential for medical wearables — and uniquely supports downlink publish back to the device, which is exactly how the alert reaches the patient's wearable. Kinesis buffers vitals bursts; EKS offers managed Kubernetes with an SLA; SNS covers the secondary care-team channel.
Python FlaskMinimal footprint, fast development, and a huge ecosystem for IoT/data workloads; easy for evaluators to read.
gunicornA production-grade WSGI server with multiple workers, unlike Flask's single-threaded development server.
Docker (slim base)213 MB image, fast pulls, a non-root user, and a built-in healthcheck — industry-standard packaging.
KubernetesSelf-healing (probes restart unhealthy pods — critical when patients depend on the monitor), horizontal scaling as the patient population grows, rolling updates with zero downtime, and config/secrets kept separate from code.
GitHub ActionsNative to the repository, free for public repos, and a YAML-as-code pipeline that is directly visible to graders.

Design decisions

  • Threshold engine decoupled from sensors — alerts.evaluate() accepts any reading dict, so swapping simulated data for real AWS IoT Core telemetry requires no change to alerting or delivery code.
  • Alert delivered to the patient's own wearable — every breach is published to vitalwatch/alerts/<device_id>, the per-device MQTT topic the wearable subscribes to, directly satisfying the question's requirement that the system alerts the patient through the wearable device.
  • Env-var configuration (12-factor) — clinical thresholds, the AWS IoT endpoint and the monitor interval are changed per environment via ConfigMap/Secret, so the same image runs unmodified from dev to production. Thresholds can even be personalised per deployment (e.g. a cardiac ward vs. general ward).
  • Graceful degradation — when the IoT endpoint is empty, wearable pushes are logged instead of crashing; the demo always works, and setting a real endpoint activates real MQTT delivery with zero code change.
  • 2 replicas + HPA — a patient-monitoring system cannot have downtime; two replicas behind the Service give high availability, and the HPA absorbs load spikes as more wearables stream data.
  • Clinically meaningful thresholds — tachycardia (>120 bpm), bradycardia (<45 bpm), hypoxemia (SpO2 <90%), fever (>38.5 °C) and hypertensive crisis (>180/110 mmHg) mirror standard early-warning criteria, so alerts are actionable rather than noisy.

Limitations

  • The in-memory patient/alert store resets on pod restart; a production deployment would use Amazon DynamoDB (registry, alert history) and Timestream (vitals time-series).
  • The wearable MQTT push is simulated, standing in for AWS IoT Core downlink publish.
  • Vital signs are simulated with occasional abnormal excursions rather than streamed from real sensors.
  • The current deployment is single-region; multi-region failover is future work.

6. Conclusion and Future Enhancements

Conclusion

VitalWatch demonstrates an end-to-end cloud-native remote patient monitoring pipeline: wearable vital-sign telemetry (heart rate, blood pressure, oxygen saturation, body temperature) is continuously evaluated against configurable clinical thresholds, and any breach is instantly pushed back to the patient's own wearable device over its per-device MQTT topic, with the care team notified in parallel. The application is containerized with Docker, published publicly on Docker Hub (shakthe/vitalwatch:v1), deployed on Kubernetes with health probes, autoscaling and zero-downtime rollouts, and delivered through an automated GitHub Actions CI/CD pipeline that tests every commit before building, publishing and deploying it into a real cluster. The design maps directly onto AWS managed services (IoT Core, Kinesis, EKS, SNS, DynamoDB), showing that the architecture is production-realistic rather than a toy exercise.

Future enhancements

  • Real wearable integration — replace the simulator with AWS IoT Core + MQTT devices (BLE wearables bridged through a fog gateway), with Kinesis for stream processing.
  • Persistent storage — DynamoDB for patients/alert history and Amazon Timestream for vitals trend analysis.
  • ML-based early warning — anomaly detection (e.g. SageMaker) on vitals trends to predict deterioration before static thresholds are crossed, and per-patient personalised thresholds.
  • Fog/edge pre-processing — run threshold evaluation on a fog node (AWS IoT Greengrass) at the patient's home so critical alerts still fire during internet outages.
  • Clinician escalation workflow — acknowledgements, escalation to emergency services if the patient does not respond to the wearable alert, and FHIR integration with hospital EHR systems.
  • Security & compliance — end-to-end encryption, audit logging and HIPAA-aligned data handling for real patient data.
  • Observability — Prometheus/Grafana dashboards and CloudWatch alarms on system health.
  • Multi-region HA — EKS in paired regions behind Route 53 health-checked failover for global resilience.
